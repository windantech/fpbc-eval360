# FPC Eval360 — GitHub and deployment

The demonstration is served as static files at **https://mel.eval360.tech/fpc/**, alongside
the ATBU build at `/mel/atbu`. Both live under the same document root:

```
/home/vantage/domains/eval360.tech/public_html/mel/
├── atbu/     → mel.eval360.tech/atbu   (the ATBU platform, PHP)
└── fpc/      → mel.eval360.tech/fpc    (this project)
```

## 1 · Create the GitHub repository

Once, from this machine:

```bash
cd ~/Documents/FPC
git remote add origin https://github.com/windantech/fpbc-eval360.git
git push -u origin main
```

If git asks for a password, paste a personal access token with `repo` scope, not your
account password. Pushing always needs a token; **pulling does not, while the repository
is public**.

> The repository is public. It carries FPC's logframe wording, the project and donor
> details, and two real staff names. No child's name appears anywhere, and the case data is
> synthetic — but the programme design and the donors' report templates are readable by
> anyone. Make it private if that is not intended.

## 2 · First deployment on the server

Over SSH, once:

```bash
cd /home/vantage/domains/eval360.tech/public_html/mel
git clone https://github.com/windantech/fpbc-eval360.git fpc
cd fpc
bash scripts/deploy_pull.sh
```

The repository is public, so cloning and pulling need no credentials and nothing secret is
stored on the server.

**If the repository is ever made private**, the clone URL has to carry a token:

```bash
git clone https://USERNAME:TOKEN@github.com/windantech/fpbc-eval360.git fpc
```

That token is then written into the clone's `.git/config`. It is outside the web root's
reachable paths and blocked by `.htaccess`, but treat it as a secret: anyone with shell
access can read it.

## 3 · Every deployment after that

From this machine:

```bash
cd ~/Documents/FPC
git add -A && git commit -m "…" && git push
```

On the server:

```bash
cd /home/vantage/domains/eval360.tech/public_html/mel/fpc
bash scripts/deploy_pull.sh
```

The script fetches, resets to `origin/main`, prints what changed, and fixes file modes. It
never runs `git clean`, so anything untracked on the server survives.

## What is and is not in the repository

| In | Out |
|---|---|
| `index.html` — the landing page at `/fpc/` | `.env` — gitignored, unlike the ATBU project |
| `fpc_eval360_demo.html` — the demonstration | `storage/` — uploads, logs, exports |
| `FPC_Eval360_User_Guide.html` — the generated guide | `vendor/`, `node_modules/` |
| The PHP scaffold (`bootstrap/`, `lib/`, `config/`…) for the future real build | |

## Rebuilding the user guide

The guide is generated by the demonstration itself — **Settings → User Guide → Build the
user guide** — and the result is saved over `FPC_Eval360_User_Guide.html`. It can also be
built without a browser:

```bash
node scripts/build-guide.js
```

Either way, commit the regenerated file so the published copy matches the published demo.

## Addresses

| Address | Goes to |
|---|---|
| `mel.eval360.tech/fpc` | The landing page |
| `mel.eval360.tech/fpc/demo.html` | The demonstration |
| `mel.eval360.tech/fpc/guide.html` | The user guide |

`demo.html` and `guide.html` are one-line forwards to the full filenames. They exist so a
link that is typed rather than tapped cannot be lost to a capital letter.

## A note on the subfolder

Everything is relative — `index.html` links to `fpc_eval360_demo.html`, not to `/fpc/…` —
so the same build works at `/fpc/`, at a different path, or opened straight from disk.
Nothing needs configuring for the subdirectory.
